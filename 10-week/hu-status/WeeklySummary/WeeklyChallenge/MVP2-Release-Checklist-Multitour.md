service; the saga resumes or ends `FAILED` for a person, as in section 4.

## 4. Demo script with an injected failure

Goal: show that the system stays consistent when a participant fails in the middle of a process that
touches two domains. The process is `onboard-tenant` (tenant in `identity-audit`, administrator in
`security`).

| Step | Action | Expected result |
|---|---|---|
| 1 | Through the gateway, start the saga with a new `Idempotency-Key`. | `201` with the saga; status `COMPLETED`; the tenant is `ACTIVE`; the administrator can sign in. |
| 2 | Repeat the same request with the same key. | `200`, the same saga, no step runs again. |
| 3 | **Injected failure A (definitive rejection):** start a saga with an administrator that `security` rejects (for example an e-mail that is already used in that tenant). | Step 2 is refused; step 1 is compensated; the saga ends `COMPENSATED` with `failedStep = CREATE_ADMINISTRATOR`; the tenant is not left pending; the identifier is free again. |
| 4 | **Injected failure B (participant down):** stop the `security` container and start a saga. | The call times out: the outcome is unknown, so nothing is undone and the saga ends `FAILED` for a person, which is the rule of the norm (a step whose outcome is unknown is never compensated blindly). |
| 5 | Start `security` again and consult the saga. | The state persists: `FAILED`, with a sanitized detail, and no password anywhere. |
| 6 | Show the events: the tenant status event leaves the outbox and the relay marks it published. | The copy of the tenant in `security` has the newest status; delivering the event twice changes nothing. |

The expected results are the behaviours that the unit tests of the saga already assert with fakes
(`TestA_step_two_failure_compensates_step_one`, `TestA_unknown_outcome_at_step_two_ends_failed_without_compensating`).
**They have not been observed against the real containers yet; that rehearsal is the open item 5.**
